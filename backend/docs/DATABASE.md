# Database Structure

SQL Server (Azure SQL in production, LocalDB for local dev), schema managed by EF Core
Code-First migrations. Source of truth is `src/Ngila.Api/Data/Migrations/`; this document is a
human-readable summary of that migration output — if the two ever disagree, the migration is
correct.

Two kinds of tables:

- **Identity tables** (`AspNet*`) — generated by ASP.NET Core Identity. `AspNetUsers` is extended
  with a handful of Ngila-specific columns; the rest are Identity's standard shape.
- **Domain tables** (`RefreshTokens`, `VendorProfiles`, `CustomerProfiles`, `Categories`,
  `FeedPosts`, `Reviews`, `Notifications`, `Reports`, `ActivityLogEntries`) — Ngila-specific,
  defined in `src/Ngila.Api/Models/Entities/`.

There is currently no Admin-specific table: an Admin is just an `AspNetUsers` row with the
`Admin` role and no `VendorProfile`/`CustomerProfile` row.

## Table reference

### AspNetUsers

One row per person, regardless of role (Admin/Vendor/Customer live here via `AspNetUserRoles`,
not as separate user tables).

| Column | Type | Notes |
|---|---|---|
| `Id` | `uniqueidentifier` PK | |
| `FirstName` | `nvarchar(100)` NOT NULL | Ngila-specific |
| `LastName` | `nvarchar(100)` NOT NULL | Ngila-specific |
| `Gender` | `int` NULL | Ngila-specific, optional. Serialized as a string (`"Male"`) over the API — see the `Gender` enum below |
| `AdminTitle` | `int` NULL | Ngila-specific. Only meaningful for `Admin`-role rows — the permission tier within Admin (see the `AdminTitle` enum below). Also carried as an `admin_title` JWT claim so authorization policies don't need a DB round-trip |
| `IsActive` | `bit` NOT NULL | Ngila-specific — soft disable without deleting the account |
| `CreatedAt` | `datetime2` NOT NULL | Ngila-specific |
| `LastLoginAt` | `datetime2` NULL | Ngila-specific |
| `UserName` / `NormalizedUserName` | `nvarchar(256)` | Set to the email; unique index `UserNameIndex` on the normalized form |
| `Email` / `NormalizedEmail` | `nvarchar(256)` | Non-unique index `EmailIndex` on the normalized form (Identity's default — uniqueness is enforced at the app layer via `RequireUniqueEmail`) |
| `EmailConfirmed` | `bit` NOT NULL | Login is blocked until true |
| `PasswordHash` | `nvarchar(max)` | PBKDF2-HMACSHA256, salted, via Identity's `PasswordHasher` |
| `SecurityStamp` / `ConcurrencyStamp` | `nvarchar(max)` | Identity internals (stamp invalidation, optimistic concurrency) |
| `PhoneNumber` / `PhoneNumberConfirmed` | | Optional, collected at registration |
| `TwoFactorEnabled` | `bit` | Not currently used by the API surface, reserved |
| `LockoutEnd` / `LockoutEnabled` / `AccessFailedCount` | | Drive the 5-attempt / 15-minute lockout policy |

### AspNetRoles / AspNetUserRoles

Standard Identity role tables. Three roles are seeded at startup (`Data/DbSeeder.cs`): `Admin`,
`Vendor`, `Customer`. A user is expected to hold exactly one of these, though Identity's schema
technically allows more.

### AspNetUserClaims, AspNetUserLogins, AspNetUserTokens, AspNetRoleClaims

Standard Identity tables, currently unused by application logic beyond what Identity itself
needs (`AspNetUserTokens` holds the email-confirmation / password-reset token state under the
hood via the token providers). Present for forward-compatibility (e.g. external login providers,
per-user claims) rather than actively queried today.

### RefreshTokens

Backs the rotating refresh-token flow in `AuthService`/`TokenService`.

| Column | Type | Notes |
|---|---|---|
| `Id` | `uniqueidentifier` PK | |
| `UserId` | `uniqueidentifier` FK → `AspNetUsers.Id`, cascade delete | |
| `TokenHash` | `nvarchar(256)` NOT NULL, **unique** | SHA-256 hash of the raw token. The raw 256-bit CSPRNG token is only ever returned to the client once, at issuance — never persisted. |
| `ExpiresAt` | `datetime2` NOT NULL | 7 days from issuance |
| `CreatedAt` | `datetime2` NOT NULL | |
| `CreatedByIp` | `nvarchar(64)` NULL | |
| `RevokedAt` | `datetime2` NULL | Null = still active |
| `RevokedByIp` | `nvarchar(64)` NULL | |
| `ReplacedByTokenHash` | `nvarchar(max)` NULL | Set when rotated, points at the token that replaced this one |
| `ReasonRevoked` | `nvarchar(max)` NULL | e.g. `"Replaced by new token"`, `"Token reuse detected"`, `"Password was reset"` |

A row is never deleted — revoked/expired rows stay for audit purposes. `IsActive` (computed, not
a column) = `RevokedAt is null && ExpiresAt > now`.

### VendorProfiles

Either a claimed vendor (1:1 with an owning `AspNetUsers` row, enforced by the filtered unique
index on `UserId`) or an **unclaimed, community-added** listing (`UserId IS NULL`) — the core
mechanic behind Ngila's "add a vendor nobody's claimed yet" feature.

Note that a `Vendor`-role `AspNetUsers` row can also exist with **zero** matching `VendorProfiles`
rows: `POST /api/auth/register` (`userType: "Vendor"`) only creates the account (personal
details), not a shop profile - that's set up separately via `PUT /api/vendors/me` once logged in.
The alternative path, `POST /api/vendors/{id}/claim`, creates the account *and* attaches an
existing unclaimed `VendorProfile` in one step, skipping that gap entirely.

| Column | Type | Notes |
|---|---|---|
| `Id` | `uniqueidentifier` PK | |
| `UserId` | `uniqueidentifier` NULL, FK → `AspNetUsers.Id`, `NO ACTION` on delete, filtered **unique** (`WHERE UserId IS NOT NULL`) | Null = unclaimed. `NO ACTION` (not `SET NULL`/`CASCADE`) — see the SQL Server cascade-path note below |
| `AddedByUserId` | `uniqueidentifier` NULL, FK → `AspNetUsers.Id`, `SET NULL` on delete | The customer/vendor who community-added this listing; used to notify them when it's claimed |
| `BusinessName` | `nvarchar(200)` NOT NULL | |
| `Description` | `nvarchar(1000)` NULL | |
| `Status` | `int` NOT NULL | See [`VendorStatus`](#vendorstatus-enum) below |
| `CategoryId` | `uniqueidentifier` NULL, FK → `Categories.Id`, `SET NULL` on delete | Nullable at storage level; required by both `PUT /api/vendors/me` and `POST /api/vendors` today |
| `LocationDescription` | `nvarchar(300)` NULL | Free text (e.g. "next to the taxi rank") — many informal vendors have no formal address |
| `Latitude` / `Longitude` | `decimal(9,6)` / `decimal(10,6)` NULL | Optional; vendors without coordinates get `distance: 0` in discovery responses. Exposed raw in `GET /api/vendors/{id}` so a client can build a maps deep link |
| `OpeningTime` / `ClosingTime` | `time` NULL | Used to compute `isOpen` server-side (Africa/Johannesburg local time) — never stored as a boolean directly |
| `ImageUrl` | `nvarchar(2048)` NULL | External URL only — no file upload/blob storage pipeline yet |
| `ContactPhone` | `nvarchar(30)` NULL | Fallback phone for an unclaimed listing (no owning `AspNetUsers` row to read a number from). Once claimed, the owner's own `PhoneNumber` takes over in API responses |
| `Rating` | `decimal(3,2)` NOT NULL, default `0` | Updated incrementally by `POST /api/vendors/{id}/reviews` (running weighted average) — never accepted directly from a vendor-facing request |
| `ReviewsCount` | `int` NOT NULL, default `0` | Same as `Rating` |
| `CreatedAt` | `datetime2` NOT NULL | |

### CustomerProfiles

One row per Customer user (1:1 with `AspNetUsers`, enforced by the unique index on `UserId`).
Currently just a marker row (`Id`, `UserId`, `CreatedAt`) — a deliberate placeholder to hang
future customer-specific fields (favourites, saved addresses, etc.) off without touching
`AspNetUsers`.

### Categories

Simple lookup table backing `GET /api/categories` and `VendorProfiles.CategoryId`. Seeded once
by `DbSeeder` (Food, Fresh Produce, Clothing, Barber, Repairs, Car Wash, Accessories);
`POST /api/categories` (OperationsAdmin only) adds more. No delete/rename endpoint yet.

### FeedPosts

Backs `GET /api/feed`. Read-only from the API's perspective today — there is no create/like/
comment endpoint, since the frontend's Feed screen has no compose UI yet (see
`components/FeedPost.tsx` in the customer app — the like/comment/share buttons are decorative).
Every row currently comes from `DbSeeder`.

| Column | Type | Notes |
|---|---|---|
| `Id` | `uniqueidentifier` PK | |
| `AuthorUserId` | `uniqueidentifier` FK → `AspNetUsers.Id`, cascade delete | |
| `AuthorDisplayRole` | `nvarchar(100)` NOT NULL | Flavour text next to the author's name (e.g. "Community Scout") — freeform, set only by seed data/future moderation tooling, never user input, so it carries no access-control meaning |
| `Content` | `nvarchar(500)` NOT NULL | |
| `VendorId` | `uniqueidentifier` NULL, FK → `VendorProfiles.Id`, `NO ACTION` on delete | Nullable — a post need not reference a vendor. `NO ACTION` (not `SET NULL`) because SQL Server rejects a second cascade-adjacent path back to `AspNetUsers` (this one via `VendorProfiles.UserId`) alongside `AuthorUserId`'s own cascade |
| `LikesCount` / `CommentsCount` | `int` NOT NULL | Denormalized counters, not backed by like/comment tables yet |
| `CreatedAt` | `datetime2` NOT NULL | Drives the `"15m ago"`-style relative time in API responses |

### Reviews

Backs `POST`/`GET /api/vendors/{id}/reviews`. One row per (vendor, reviewer) pair — resubmitting
a review updates the existing row (`UpdatedAt` set) rather than inserting a duplicate.

| Column | Type | Notes |
|---|---|---|
| `Id` | `uniqueidentifier` PK | |
| `VendorId` | `uniqueidentifier` FK → `VendorProfiles.Id`, cascade delete | |
| `UserId` | `uniqueidentifier` FK → `AspNetUsers.Id`, `NO ACTION` on delete | See cascade-path note below |
| `Rating` | `int` NOT NULL | 1–5 |
| `Comment` | `nvarchar(1000)` NULL | |
| `CreatedAt` / `UpdatedAt` | `datetime2` | `UpdatedAt` is null until the reviewer edits their review |

Unique index on `(VendorId, UserId)` enforces the one-review-per-reviewer rule at the database
level, not just in application code. `VendorProfiles.Rating`/`ReviewsCount` are updated in the
same transaction as each write, via a running weighted average — `Reviews` is never scanned in
full to recompute them, so the aggregate stays cheap regardless of table size.

### Notifications

Backs `GET /api/notifications` and the customer app's notification bell. Currently populated by
`DbSeeder` (demo data) and by `AuthService.ClaimVendorAsync` (notifies whoever community-added a
vendor once it's claimed) — the only real trigger that exists today.

| Column | Type | Notes |
|---|---|---|
| `Id` | `uniqueidentifier` PK | |
| `UserId` | `uniqueidentifier` FK → `AspNetUsers.Id`, cascade delete | Recipient |
| `Title` | `nvarchar(200)` NOT NULL | |
| `Body` | `nvarchar(500)` NOT NULL | |
| `VendorId` | `uniqueidentifier` NULL, FK → `VendorProfiles.Id`, `NO ACTION` on delete | Optional deep-link target |
| `IsRead` | `bit` NOT NULL | |
| `CreatedAt` | `datetime2` NOT NULL | |

### Reports

Backs `POST /api/reports` (any authenticated user files one) and the admin moderation endpoints
(`GET`/`POST .../resolve` under `/api/admin/reports`, `CanManageReports` policy). Matches the
product doc's Community Moderation section: fake businesses, wrong locations, duplicates, and
disputed/fraudulent reviews.

| Column | Type | Notes |
|---|---|---|
| `Id` | `uniqueidentifier` PK | |
| `ReporterUserId` | `uniqueidentifier` FK → `AspNetUsers.Id`, cascade delete | |
| `Kind` | `int` NOT NULL | `Flag` (targets a vendor) or `ReviewDispute` (targets a review) — see the `ReportKind` enum below |
| `Priority` | `int` NOT NULL, default `Normal` | Always `Normal` on creation today — no endpoint lets anyone escalate it yet |
| `Title` / `Detail` | `nvarchar(200)` / `nvarchar(1000)` NOT NULL | |
| `TargetVendorId` | `uniqueidentifier` NULL, FK → `VendorProfiles.Id`, `NO ACTION` on delete | Set when `Kind = Flag` |
| `TargetReviewId` | `uniqueidentifier` NULL, FK → `Reviews.Id`, `NO ACTION` on delete | Set when `Kind = ReviewDispute` |
| `IsResolved` | `bit` NOT NULL | |
| `ResolvedByUserId` | `uniqueidentifier` NULL, FK → `AspNetUsers.Id`, `NO ACTION` on delete | |
| `ResolvedAt` | `datetime2` NULL | |
| `CreatedAt` | `datetime2` NOT NULL | |

Exactly one of `TargetVendorId`/`TargetReviewId` is expected to be set, matching `Kind` — enforced
by `ReportService`/`ReportRequestValidator`, not a DB constraint. All FKs off this table other
than `ReporterUserId` are `NO ACTION` — see the cascade-path design note below; `Report` has two
direct paths to `AspNetUsers` (`ReporterUserId`, `ResolvedByUserId`) plus two more that reach it
transitively through `VendorProfiles`/`Reviews`, so only one can safely cascade.

### ActivityLogEntries

Backs the admin dashboard's "Activity" feed (`GET /api/admin/activity`). Written at a small,
deliberate set of trigger points — vendor added, vendor claimed, vendor verified, claim rejected,
report resolved — not a full audit log of every write in the system.

| Column | Type | Notes |
|---|---|---|
| `Id` | `uniqueidentifier` PK | |
| `ActorUserId` | `uniqueidentifier` FK → `AspNetUsers.Id`, cascade delete | Who performed the action |
| `Description` | `nvarchar(300)` NOT NULL | e.g. `"added Mama Mary's Kitchen"` — combined with the actor's name for display |
| `Tone` | `nvarchar(50)` NOT NULL | Display-only category driving the dashboard's colour-coded dot (`vendor-added`, `vendor-verified`, `vendor-claimed`, `claim-rejected`, `report-resolved`) — not used for querying |
| `CreatedAt` | `datetime2` NOT NULL | |

## Enums

### `VendorStatus` (`VendorProfiles.Status`)

| Value | Meaning |
|---|---|
| `0` — `PendingVerification` | Default on self-registration; not yet reviewed by an Admin |
| `1` — `Verified` | Admin has verified the business |
| `2` — `Suspended` | Admin has suspended the listing |

This is a simplified starting point, not the full lifecycle described in the product docs
(`Community Added → Pending Verification → Vendor Claimed → Verified → Active`, plus
`Temporarily Closed` / `Moved` / etc.). Community-added/claimed *is* now built, but as an
orthogonal concept - `VendorProfiles.UserId is null` means "community-added, unclaimed" - rather
than as extra `VendorStatus` values, so a listing's verification state and its claimed state can
vary independently. Extend this enum only if a genuinely new *verification* state is needed
(e.g. `Suspended` already covers admin takedown); claimed-vs-unclaimed doesn't belong here.

### `Gender` (`AspNetUsers.Gender`)

| Value | Meaning |
|---|---|
| `0` — `Female` | |
| `1` — `Male` | |
| `2` — `Other` | |

Nullable and optional everywhere it's collected (every registration DTO). Serialized as a string
over the API (`"Male"`, not `1`) via a global `JsonStringEnumConverter` in `Program.cs`.

### `UserType` (request-only, not a stored column)

| Value | Meaning |
|---|---|
| `0` — `Customer` | |
| `1` — `Vendor` | |
| `2` — `Admin` | |

Picks which of the three account types `POST /api/auth/register` creates — it's not persisted as
a column anywhere; the choice is realized as an `AspNetRoles`/`AspNetUserRoles` assignment (and,
for `Customer`, a `CustomerProfiles` row) once the account is created. See `AuthService.RegisterAsync`.

### `AdminTitle` (`AspNetUsers.AdminTitle`)

| Value | Meaning | Can do (see `Common/AdminPolicies.cs`) |
|---|---|---|
| `0` — `OperationsAdmin` | | Everything: verify/reject vendors, manage categories, resolve reports, view users, create new Admins |
| `1` — `VerificationReviewer` | | Verify/reject/request-info on vendor claims only |
| `2` — `CommunityManager` | | Resolve reports, view the admin user list |

Required (`NOT NULL` at the DTO level, though the column itself is nullable) whenever
`UserType: "Admin"` is registered; meaningless for Customer/Vendor rows. The bootstrap admin
(`AdminBootstrap:*` config) is always seeded as `OperationsAdmin`, since only that title can
create the other two.

### `ReportKind` (`Reports.Kind`)

| Value | Meaning |
|---|---|
| `0` — `Flag` | Reporting a vendor listing (fake business, wrong location, duplicate, closed) |
| `1` — `ReviewDispute` | Reporting a specific review (fraudulent, disputed by the vendor) |

### `ReportPriority` (`Reports.Priority`)

| Value | Meaning |
|---|---|
| `0` — `Normal` | Default and only value assigned today |
| `1` — `High` | No endpoint currently sets this — reserved for when escalation is built |

## Design notes

- **Why one `AspNetUsers` table instead of separate Admin/Vendor/Customer tables?** Auth
  (login, password reset, lockout, tokens) is identical across all three actors — splitting it
  three ways would triplicate security-sensitive code for no benefit. Role-specific data lives
  in the 1:1 profile tables instead.
- **Why hash refresh tokens?** Same reasoning as password hashing: `RefreshTokens` is a
  database table, and a leaked backup or SQL-injection read shouldn't hand out live session
  tokens. Only the SHA-256 hash is stored; the raw value exists only in the HTTP response and
  the client's storage.
- **Why cascade delete everywhere?** All child tables (`RefreshTokens`, `VendorProfiles`,
  `CustomerProfiles`, and Identity's own join tables) delete with their `AspNetUsers` row —
  there's no soft "orphaned profile" state to reason about. Account deactivation should go
  through `IsActive = false`, not a row delete, if the history needs to be kept.
- **Why is `RefreshTokens` append-only?** Revoked/expired tokens are kept (not deleted) so
  `ReplacedByTokenHash` and `ReasonRevoked` form an auditable chain — this is what lets the
  reuse-detection logic in `AuthService.RefreshTokenAsync` notice a revoked token being replayed
  and respond by revoking every active session for that user.
- **Why do so many FKs use `NO ACTION`/`Restrict` instead of `CASCADE`/`SET NULL`?** SQL Server
  refuses to create a cascading (`CASCADE` or `SET NULL`) FK if it would give a table a second
  path back to an ancestor it can already reach another cascading way (error 1785, "may cause
  cycles or multiple cascade paths"). `AspNetUsers` is that ancestor almost everywhere, so the
  *second* cascading FK into any table that already has one gets `NO ACTION` instead:
  `FeedPosts.VendorId` (alongside `AuthorUserId`'s cascade), `Reviews.UserId` (alongside
  `VendorId`'s cascade), `Notifications.VendorId` (alongside `UserId`'s cascade), and
  `VendorProfiles.UserId` itself (alongside `AddedByUserId`'s `SET NULL`). Practically: deleting a
  user who still owns a claimed `VendorProfile` is blocked at the database level rather than
  silently cascading — there's no user-deletion feature yet, so this hasn't needed a workaround.
- **Why is the Admin permission tier (`AdminTitle`) a JWT claim, not just a DB lookup per
  request?** It's stored on `AspNetUsers` either way, but `TokenService` also copies it into the
  access token as an `admin_title` claim at login/refresh time, and `Program.cs` defines named
  authorization policies (`CanManageVendorVerification`, etc.) that check the claim directly.
  This avoids a DB round-trip on every admin request just to answer "is this caller allowed to
  do this" — the tradeoff is that changing someone's `AdminTitle` doesn't take effect until they
  next log in or refresh (there's no "revoke this token's claims immediately" endpoint).

## Working with migrations

```bash
cd backend/src/Ngila.Api

# after changing an entity in Models/Entities/ or ApplicationDbContext.OnModelCreating
dotnet ef migrations add <DescriptiveName> -o Data/Migrations

# apply pending migrations to the configured connection string
dotnet ef database update
```

Migrations run automatically on startup in `Program.cs` (`db.Database.MigrateAsync()`), so
deploying a new version to Azure applies any pending migration before the app starts serving
traffic.
